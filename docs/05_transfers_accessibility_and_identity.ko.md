## 선호도보다 먼저 실현 가능성을 판단하기

엄격한 접근성 제약은 선호도 가중치가 아니다. 계단으로만 이어진 연결은 이동 시간이 아무리 뛰어나도 이용할 수 있게 되지 않는다. 마찬가지로 역에 엘리베이터가 설치되어 있다는 이유만으로, 필수 운영 증거 필드가 누락된 상태를 “아마 괜찮을 것”이라고 볼 수는 없다.

설치 증거와 운영 검증은 의미가 다르다. 엘리베이터가 있다는 사실을 알아도 그것이 운행 중임을 입증하지는 못한다. 마찬가지로 조회 타임스탬프는 상태를 확인한 시점을 입증하지 않는다. 이 실습은 어느 사실도 추론하려 하지 않고 명시적인 증거 플래그를 제공한다.

이 실습은 `step_free`와 `verified`로 이 차이를 드러낸다. 계단으로 확인된 간선은 엄격 모드에서 제외한다. 알 수 없거나 검증되지 않은 간선이 있으면 보수적인 전체 스냅샷 입력 수용 정책에 따라 `ACCESSIBILITY_UNAVAILABLE`이 발생한다. 이는 교육을 위한 단순화이며, 전체 프로덕션 범위 지정 규칙은 아니다.

## 하나의 마법 같은 환승 시간이 아니라 세 가지 보행

ENTRY는 출발지 끝점에서 첫 승차 플랫폼까지 승객을 이동시킨다. TRANSFER는 하차 상태를 다음 승차 상태에 연결한다. EXIT는 마지막 플랫폼에서 목적지 끝점까지 승객을 이동시킨다.

합성 픽스처는 이 간선들을 각각 방향이 있는 형태로 제공한다. 반대 방향 간선을 추론하지 않는다. `WalkPolicy`의 소요 시간 계수는 명시적인 올림 규칙에 따라 허용된 각 간선의 소요 시간을 바꾼다. 기본값과 예제의 60초 승차 여유 시간은 실습에서 선택한 값이며, 보편적인 대중교통 정책 값이 아니다.

더 풍부한 상태에는 진입 노선, 플랫폼, 전이 식별자, 이동성 프로파일, 경로별 증거가 필요할 수 있다. 이 픽스처에서 `X`에 도착하는 것은 `Y`에서 준비가 완료된 것과 같지 않다. 방향이 있는 환승에 120초가 걸린 다음 승차 여유 시간이 더해진다.

## 잘못된 간선 순서로 도보 경로 전파 설명하기

입력에 `C -> D`, `B -> C`, `A -> B` 순서로 나열되어 있다고 하자. `A`에서 시작하면 한 번의 순회로는 `B`에만 도달한다. 유용한 앞쪽 간선들을 이미 지나쳤기 때문에 완전히 유효한 `D`까지의 보행을 놓친다.

`close_footpaths`는 더 나은 도달 가능 보행 라벨이 없을 때까지 개선 사항을 처리한다. 음수가 아닌 비용과 엄격한 개선 조건 덕분에 소요 시간이 0인 순환도 종료된다. 힙은 불변 라벨 객체를 사용해 오래된 큐 항목을 안전하게 버린다.

음수 보행 시간은 입력 구성 단계에서 거부한다. 이를 0으로 “수정”하지 않는다. 그렇게 하면 잘못된 입력을 숨기고 실현 가능한 환승을 지어낼 수 있기 때문이다.

## 한 번 바인딩한 뒤 계산하기

계산 내내 하나의 입력 컨텍스트를 유지하라. 프로파일에서 한 구간의 시간표와 다른 구간의 실시간 정보 또는 보행 정책을 섞으면 한 번도 동시에 존재한 적 없는 결과 집합이 만들어질 수 있다. 로컬 프로파일 호출은 전체 시간 범위에 하나의 컴파일된 시간표와 하나의 보행 정책을 전달받는다.

[`Snapshot`](../src/realtime.py)은 이 중 일부를 보여 준다. 번들과 운행일이 일치해야 하고, 유효성을 검사하며, 알 수 없는 운행편 발생 건을 거부하고, 원본 시간표를 변경하지 않는다. 업데이트 모델의 범위는 의도적으로 좁다. 암호학적 검증과 서비스 엔드포인트는 구현되어 있지 않다.

이 경계는 중요하다. 해시처럼 생긴 필드는 서명된 설명 파일이 아니다. 고정된 Python 객체는 활성화 확인 기록이 아니다. 로컬 테스트는 배포된 요청 관측이 아니다.

## 실패도 API의 일부다

서로 다른 실패는 승객과 운영자의 서로 다른 질문에 답한다.

| 상황 | 실습 동작 | 구분을 유지해야 하는 이유 |
|---|---|---|
| 잘못된 시간 또는 알 수 없는 정류장 | 타입이 지정된 입력 오류 | 쿼리가 입력 수용 검증을 통과하지 못했다 |
| 엄격한 접근성 증거를 알 수 없음 | `ACCESSIBILITY_UNAVAILABLE` | 실현 가능성을 확정할 수 없었다 |
| 오래되었거나 일치하지 않는 실시간 정보 | 타입이 지정된 스냅샷 오류 | 요청한 입력 식별성을 사용할 수 없다 |
| 입력 수용 검증을 통과한 실현 가능 경로가 없음 | 빈 결과 | 경로 없이 검색이 완료되었다 |
| 작업량/프런티어 용량 초과 | 타입이 지정된 용량 오류 | 완전성을 보존할 수 없었다 |
| 기한/취소 | 타입이 지정된 실패 | 부분적이거나 늦은 작업을 게시해서는 안 된다 |

오류 코드는 로컬 Python API에 속한다. 이 저장소는 네트워크 응답 스키마를 정의하지 않는다.

모든 예외를 잡아서 마지막으로 성공한 여정을 반환하지 마라. 권위 있는 계산의 실패를 성공으로 바꾸기 위해 레거시 경로 서비스를 다시 실행하지 마라. 사용자가 명시적으로 재시도하면 새로운 유효한 컨텍스트를 사용하는 새 요청이 되며, 실패한 요청의 이름표를 바꿀 권한이 생기는 것은 아니다.

## 표현은 계산의 의미를 보존해야 한다

예제는 현재 결과를 출력하고, 여정이 없는 입력 수용 검증을 통과한 단일 시점 탐색에는 `NO_ROUTE`를 출력한다. 이전의 성공한 여정을 재사용하지 않는다. 향후 UI도 마찬가지로 완료되었지만 비어 있는 검색을 거부되거나 중단된 계산과 구분해야 한다.

프로파일에는 [`Profile.at`](../src/profile.py)이 반환한 구간을 사용하라. 구간 사이에 가상의 열차를 보간하거나 오류를 이전 구간으로 대체하지 마라. 승객 UI와 그 상호작용 동작은 이 실습의 범위를 벗어난다.

## 연습 문제와 답

계단으로 확인된 간선의 `step_free`를 `None`으로 바꿔 보라. 엄격한 결과가 단지 또 하나의 느린 경로가 아니라 입력 수용 오류가 되는 이유는 무엇인가? 이 실습에서는 엄격한 전체 스냅샷의 증거가 알려져 있어야 한다. 이 보수적인 정책은 “알 수 없음”이 암묵적으로 “접근 가능”으로 취급되는 것을 막는다.

그런 다음 프로덕션에서 더 선별적으로 처리하려면 무엇이 필요한지 설명하라. 실제로 입력 수용 검증을 통과한 그래프/쿼리에 연결된 범위별 증거 요구 사항과 완전한 실패 의미론이 필요하며, 일괄적인 `None -> True` 변환은 답이 아니다.
